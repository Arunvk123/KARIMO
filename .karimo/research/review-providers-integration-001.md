Working notes for understanding (and later extending) the two built-in review
providers — Greptile and Claude Code Review — before adding support for a
custom code reviewer.

---

## Questions Investigated

1. Are the reviewers mentioned in commit messages or PR descriptions?
2. What triggers each reviewer?
3. How does the KARIMO agent pick up review comments?
4. Do the reviewers only comment, or do they also change PR status / merge?

## 1. Commit Messages / PR Descriptions

**Neither provider is referenced in commits or PR bodies.**

- PR body template (`pm.md` ~L1500-1523): task id/title, PRD, wave, complexity,
  model, description, success criteria, files changed, KARIMO footer. No reviewer mention.
- Commits: Conventional Commits, no reviewer reference.
- The PR ↔ reviewer link is made through **GitHub labels + app installation only**.

## 2. Triggers

Both manifests declare `on_pr_create: null` and `on_revision_push: null`.
**KARIMO never calls a provider directly** — they react to GitHub events.

| | Greptile | Claude Code Review |
|---|---|---|
| **Install** | Greptile GitHub App + repo indexed in dashboard (`/karimo:configure --greptile`) | Claude GitHub App, enabled at `claude.ai/admin-settings/claude-code` (Teams/Enterprise only; `/karimo:configure --code-review` only prints steps) |
| **Files KARIMO writes into target repo** | `.greptile/config.json` (`labels: ["karimo"]`, `triggerOnUpdates: true`, `statusCheck: true`), `.greptile/rules.md` (generated by `karimo-greptile-rules-writer`; must be **manually linked** in Greptile dashboard → Custom Context), `.github/workflows/karimo-greptile-trigger.yml` | `REVIEW.md` at repo root (from `REVIEW_TEMPLATE.md`, with `never_touch` / `require_review` boundaries injected) |
| **First review trigger** | PM creates PR, then applies labels `karimo,karimo-{slug},wave-{n},complexity-{c}` (`pm.md` ~L1496). The `labeled` event with `karimo` fires the workflow, which posts an `@greptileai` comment (skips if Greptile already reviewed or comment exists). Workflow exists because Greptile's own label filter races with label-after-create. | Opening the PR. The Claude App runs as a **check run** whose name matches `[Cc]ode [Rr]eview`. |
| **Re-review after fixes** | Automatic on push (`triggerOnUpdates: true`) | Automatic on push |

## 3. How KARIMO Picks Up Review Comments (PM-Reviewer)

The PM spawns a **PM-Reviewer** per task PR when review is configured and
cadence allows (`should_spawn_reviewer()` in `pm.md` ~L1530).

### Step 2 — Poll (`pm-reviewer.md` ~L385-435)
- 20 attempts × 30 s = **10 min max**
- Greptile: `gh pr view --json comments`, match `confidence.*[0-5]/5|[0-5]/5.*confidence`
- Code Review: `gh pr checks`, wait for check run name `[Cc]ode [Rr]eview` with `status == completed`
- **Timeout → pass with warning** ("Proceeding without automated review")
  - ⚠ Code Review averages ~20 min; may exceed the 10-min window

### Step 3 — Parse (`hooks.on_review_complete`, stdout is eval'd as `key=value`)

`parse_greptile.sh` (env: `PR_NUMBER REPO_OWNER REPO_NAME THRESHOLD`):
```
score=N             # from last comment matching X/5
passed=true|false   # score >= THRESHOLD (default 5)
p1_count=N          # inline comments containing "P1:"
p2_count=N
p3_count=N
error=no_review_found  # when no comment matched (score=0, passed=false)
```

`parse_code_review.sh` (env: `PR_NUMBER REPO_OWNER REPO_NAME BLOCK_ON_RED IGNORE_NITS IGNORE_PREEXISTING`):
```
passed=true|false   # false iff BLOCK_ON_RED && red_count > 0
red_count=N         # inline comments containing 🔴
yellow_count=N      # 🟡
purple_count=N      # 🟣
```
- ⚠ `ignore_nits` is a **no-op** — 🟡 never blocks regardless of config.
- 🟣 pre-existing always ignored.

### Step 3.5 — Classify each finding
- **actionable** → goes to revision worker
- **future-work-overlap** → appended to `.karimo/prds/{slug}/deferred_findings.md` (surfaced at merge gate)
- **false-positive-factual** → skipped

### Step 4 — Decision tree + labels
| Outcome | Label(s) | Effect |
|---|---|---|
| pass | `greptile-passed` | done |
| all findings deferred/skipped | `greptile-passed-classified` + PR comment about deferred count | done |
| fail + `on_findings: comment-only` | `greptile-comment-only` / `code-review-comment-only` + findings comment | merge permitted |
| fail + `on_findings: halt` | `needs-revision` | spawn revision worker |
| max loops / semantic loop on Opus | `blocked-needs-human` | verdict `escalate`, task `needs-human-review` |

### Step 5 — Revision loop
- Spawns `karimo-implementer` (or `-opus` when escalation triggers) with the findings
  embedded in the prompt (`pm-reviewer.md` ~L860-877). Worker pushes → provider
  auto-re-reviews → loop repeats.
- Escalation: after `models.escalation.after_failures` (default 1) or trigger keywords
  (`architectural_issues`, `type_system_issues`).
- Circuit breakers: 3 revision loops, 5 total loops, semantic loop (same
  files-changed + error fingerprint as previous attempts).

### Step 7 — Failure hook
`.karimo/hooks/on-failure.sh` runs after each failed attempt with
`TASK_ID PRD_SLUG PR_NUMBER PR_URL FAILURE_REASON ATTEMPT MAX_ATTEMPTS ESCALATED_MODEL …`.

### State
`status.json` per task: `review.provider`, `threshold`, `scores[]`, `loop_count`,
`last_score`, `passed`, `last_reviewed_at`.

## 4. Comment-only vs Status Change

**Both providers only comment. Neither approves / requests changes / merges.**

- **Greptile:** summary comment (X/5 confidence, issues table, diagram) + inline
  `P1/P2/P3` comments. With `statusCheck: true` it also sets a **commit status**,
  but KARIMO ignores that and reads the comment score.
- **Code Review:** a **check run** + inline 🔴/🟡/🟣 comments; auto-resolves threads
  when a later push fixes the issue. KARIMO waits on the check run.
- All PR-state changes come from **KARIMO** (labels above, PM merge step).
  Branch protection requiring the Greptile status / Code Review check is a GitHub
  setting the user configures — KARIMO does not set it up.

## Gaps / Drift Noticed

1. **Config shape drift** — `configure.md` writes legacy
   `review: {provider, threshold, max_revision_loops}` and `pm-reviewer.md` reads
   those keys; `REVIEW-PROVIDERS.md` documents `review.providers.{active, config, registered}`.
   Legacy keys are what actually works today.
2. **`ignore_nits` no-op** in `parse_code_review.sh`.
3. **10-min poll vs ~20-min Code Review** — timeout silently passes.
4. **Greptile detection is regex on free text** (`X/5` + "confidence") — fragile
   if Greptile changes its comment format.
5. `.greptile/rules.md` requires a manual dashboard step; nothing verifies it.
6. `karimo-greptile-trigger.yml` skips only when `github.repository == opensesh/KARIMO`
   (not the fork `Arunvk123/KARIMO`).

## Implications for a Custom Code Reviewer (next step)

Minimum contract a new provider must satisfy (per `REVIEW-PROVIDERS.md` + PM-Reviewer):

- `.karimo/providers/{name}/manifest.yaml` with `name`, `version`, `description`,
  `pricing_model`, `capabilities`, `hooks.on_review_complete`, optional
  `hooks.on_pr_create`, `config_schema`.
- `on_review_complete` script printing `passed=true|false` (+ `score=N` if
  `score_output: true`) as `key=value` on stdout; env vars listed in
  `REVIEW-PROVIDERS.md` (`PR_NUMBER`, `REPO_OWNER`, `REPO_NAME`, `THRESHOLD`, …).
- **But** `pm-reviewer.md` Step 2 polling and Step 4 decision tree are still
  hard-coded per provider (`greptile` / `code-review` branches, label names).
  A truly pluggable provider needs the PM-Reviewer to:
  - poll via a provider-supplied "is review ready?" hook (or generic strategy),
  - use provider-neutral labels (or labels from the manifest),
  - build the revision prompt from the parser's findings output generically.
- `configure.md` needs a path to register the provider (`review.provider: {name}`
  today; `review.providers.active` per docs).

Open questions to resolve when continuing:
- Trigger model for the custom reviewer: GitHub App / Action / local script via `on_pr_create`?
- Finding format: inline comments with a severity marker the parser can grep?
- Should we fix the config-shape drift as part of this work or keep legacy keys?
